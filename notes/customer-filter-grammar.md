# Сборка фильтра по клиентам через URL (`newcustomers/customers/?filter=…`)

Как **собрать** (а не только прочитать) любой фильтр по клиентам, опираясь
на то, что конструктор зеркалит всё в адресную строку. Парная заметка к
«читающим» приёмам ([`customer-profile-extraction.md`](customer-profile-extraction.md),
react-flow / segmentation). Полная грамматика языка `?filter` — в каноне
[`../../knowledge/reference/mindbox-фильтр-клиентов.md`](../../knowledge/reference/mindbox-фильтр-клиентов.md);
здесь — **как этим пользоваться и где грабли**.

## Что за страница

`https://<тенант>.mindbox.ru/newcustomers/customers/?filter=<выражение>` —
SPA. Конструктор фильтра (кнопки «Добавить фильтр» / «Добавить группу ИЛИ» /
«Применить») и адресная строка — два представления одного дерева условий.
В доке Mindbox язык `?filter` **не описан** (только логика И/ИЛИ и типы
условий) — отсюда эта заметка.

## Базовый цикл (снять любой токен — ~30 сек)

1. Собери условие в конструкторе → **«Применить»** (URL обновляется только
   по «Применить», не при добавлении условия).
2. `decodeURIComponent(location.search)` в консоли (или просто скопируй
   адресную строку) → получил шаблон токена.
3. Подставь свои значения, собери `?filter`, проверь обратной навигацией:
   открой URL → конструктор должен отрисовать ровно то условие, счётчик —
   дать осмысленное число.

`location.search` переживает закрытие меню — **URL читай через JS, а список
полей/операторов снимай скриншотом** (меню закрывается на blur, который
даёт вызов `javascript_tool`).

## Каркас языка (кратко, детали — в каноне)

- `filter = clause+`, каждая клауза `and(node)` или `or(node)`.
- **На одном уровне все клаузы одной связки**: `and(A)and(B)` = И,
  `or(A)or(B)` = ИЛИ. Смешивать `and`+`or` на уровне нельзя.
- Смешанная логика — вложением: `(A И B) ИЛИ (C И D)` →
  `or(and(A)and(B))or(and(C)and(D))`.
- Скаляр: `field(cv(<сравнение>)filter-mode(<режим>))`.
  `filter-mode(Concrete)` = «заполнен и», `filter-mode(Absent)` = «не
  заполнен» (тогда `cv` отсутствует).
- Коллекция (заказы/позиции/действия): `collection(f(and(<поля>))aggregate(name(any)))`
  — внутри `f(...)` **та же грамматика and/or** по полям элемента.
  Количество: `retail-orders(aggregate(name(count)params(from(N)to(M))))`.
- Дата действия в окне: `useractivity(f(and(datetime(cv(m(Value)su(<UTC>)eu(<UTC>))filter-mode(Concrete))))aggregate(name(any)))`
  — токен **`datetime`** (момент UTC `Д.М.ГГГГ_ч_м_с_мс`, мс можно пусто), su=начало, eu=конец.
- Сегмент: `segments(ss((sid(<internalId>)m(segmentation)))m(or)f(segment))`.

Готовые подставляемые шаблоны — таблица «Готовые примеры» в каноне, или
генератор [`../../scripts/mindbox_filter.py`](../../scripts/mindbox_filter.py).

## Грабли (проверено вживую 2026-06-19, usmall)

- **Дата действия — только `datetime`.** Тупики (дают «Невалидный фильтр»):
  встроенный ярлык `is-registration-action` **не комбинируется** с датой/периодом
  в одном `useractivity`; `creationdatetime` и `customerActionCurrentDateTime` в
  связке с регистрацией — невалидны. «Зарегистрировался в период» строго через
  ярлык не собирается — путь: общий «Действие клиента» + `datetime` (+ при нужде
  шаблон действия), либо пересчитываемый сегмент.
- **Неизвестный токен → «Удаленный фильтр», а не ошибка.** Опечатка в имени
  поля не валит фильтр: движок оборачивает токен в `deleted(...)` и рисует в
  дереве красный «Удаленный фильтр» (прецедент 2026-08-27: `message-open-status`
  вместо `message-opened-status`). Это главный сигнал «имя угадано неверно» при
  обратной навигации.
- **Движок нормализует URL.** На «вольный»/устаревший фильтр Mindbox показывает
  плашку «преобразован, пользуйтесь обновлённой ссылкой» и сам чинит синтаксис
  (хвост мс `_0_0_0`→`_0_0_`). Если была плашка — бери URL из адресной строки.
- **⚠️ ИЛИ из UI ненадёжно попадает в URL.** «Добавить группу ИЛИ» + тумблер
  И/ИЛИ в прогонах давали `and()and()` (то есть И) после «Применить», хотя
  в UI группа была помечена ИЛИ. **Надёжно:** задавать ИЛИ прямо в URL
  (`or(...)`) и открывать навигацией; либо после «Применить» убедиться, что
  в `?filter` стоит `or` и счётчик вырос. Проверка счётчиком разводит
  однозначно: `or(Имя=Иван)or(Имя=Мария)` → и Иваны, и Марии; `and(...)and(...)`
  тех же двух → 0.
- **`internalId` сегмента в UI скрыт**, но виден в URL (`sid(...)`) сразу
  после выбора сегмента в конструкторе — это самый быстрый способ его узнать.
- **«Некорректное значение» в условии** = глюк отрисовки, перезагрузить
  страницу (см. [`ui-quirks.md`](ui-quirks.md)).
- Коллекционные условия по товару/категории тяжёлые — дока советует вынести
  в пересчитываемый сегмент и фильтровать по `segments(...)`
  (см. `../../knowledge/reference/mindbox-пересчёт-сегментов.md`).

## Грабли автоматизации (Claude in Chrome)

- **Масштаб страницы (DPI) плавает между скриншотами** — клик по «голым»
  координатам часто промахивается. Кликай по `ref` из `find`/`read_page`,
  координаты — только когда ref недоступен (пункты выпадающих меню).
- **Меню признаков перерисовывается/сворачивает категории** при скролле и
  ре-рендере. Надёжнее: открыть «Добавить фильтр» → ввести имя поля в строку
  поиска «Название фильтра» (она же фильтрует дерево, включая под-категории
  «Заказы…»), затем кликнуть лист.
- **Меню закрывается на blur** при `javascript_tool` — поэтому список читаем
  скриншотом, а URL (он переживает) — через JS.
- `Page.captureScreenshot` иногда таймаутит на занятом рендерере — повторить.

## Стоимость

Снять один токен — ~30 сек (собрать условие + «Применить» + прочитать URL).
Собрать готовый фильтр из известных токенов — мгновенно (правка строки).
Полный реверс грамматики (этот заход) — ~десятки действий; результат
зафиксирован, повторять не нужно.
