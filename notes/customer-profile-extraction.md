# Извлечение карточки клиента (`newcustomers/<id>`) из MindBox UI

Как снять данные клиента — **быстро** (обзор) или **полно и проверяемо**
(аудит: «почему клиент получил/не получил коммуникацию, в каком состоянии
был в этот момент, как жил с момента прихода в базу»). Главное правило
заметки: **минимум догадок, максимум того, что реально видно** — каждая
строка истории клиента может быть важна.

## Что за страница

`https://<тенант>.mindbox.ru/newcustomers/<id>/view/personal-info` — SPA
(React, федеративные модули). Вкладки и под-виды — через URL (навигацией):

- `?tab=segments|history|...` — вкладка;
- `?segments=history` — Сегменты → «История» (по умолчанию «Текущие»);
- `?<id>-activityType=Orders,Mailings,Registrations,Personalization,…` —
  фильтр Ленты по типам активности;
- `?drawer=id-history` — «История идентификаторов»;
- `?drawer=push-and-devices` — «Устройства».

Данные **НЕ** в `__APOLLO_CLIENT__` (его кэш по клиенту пуст). Каждая
секция дёргает **именованную GraphQL-операцию**:

```
POST https://<тенант>.mindbox.ru/graphql?queryName=<OperationName>
```

`?queryName=<Op>` обязателен (без него `/graphql/` → HTML). Авторизация —
заголовок **`Authorization: Bearer …`** (cookie без него → `401`).
Интроспекция схемы **отключена**.

## Режимы — лестница усилий (эскалируем по необходимости)

Не «снять всё на всякий случай», а подниматься на следующий уровень
**только когда вопрос этого требует** — так не делаем лишних телодвижений
там, где хватает дешёвого шага.

| Что нужно ответить | Уровень |
| --- | --- |
| Кто клиент, что недавно происходило, какие статусы рассылок | **A. `get_page_text`** |
| Скрытое/структурное по ОДНОЙ секции (internalId сегмента, причина перехода, before/after изменения) | **B-точечно** (реплей одной операции) |
| Полный аудит: вся история «с момента прихода»; «почему получил/не получил коммуникацию» | **B-полный** (реплей + пагинация до конца + словари) |

На большинство вопросов хватает A. В B проваливаемся адресно — за конкретным
скрытым полем; тяжёлый B-полный (пагинация всей ленты до первого события)
запускаем только под аудит.

### A. Быстрый обзор — `get_page_text` (без auth, без JS)

Это извлечение **текста отрисованной страницы** (DOM как есть, точный текст —
не скрин/OCR), и этого часто достаточно:

- `personal-info` — ФИО, телефон, email, дата рождения, пол, часовой пояс,
  Mindbox ID, идентификатор на сайте, дисконтные карты, устройства;
- **Лента активности уже отрисована тут же** — каждая запись с **именем
  рассылки, статусом (Отправлена / Открыта / Не доставлена / …), временем
  отправки и временем смены статуса**, плюс действия (заказы, авторизации,
  выдача промокода). Имена уже подставлены — джойны не нужны.

Подгрузить больше строк ленты/истории — проскроллить и перечитать.
**Ограничение:** только загруженное окно (не вся история), нет скрытых ID
(`internalId` сегментов), нет структуры для программной обработки. Если
что-то запечено в картинку (баннер/оффер) — третий, ещё более дешёвый для
чтения, но «слепой» запасной вариант: `screenshot`.

### B. Реплей операций — точечно или полно

**B-точечно** — нужно скрытое/структурное поле по одной секции: реплей
**одной** операции этой секции (например `CustomerSegmentsDataQuery` за
`internalId`). **B-полный** — нужна вся история/аудит: реплей нужных
операций **с пагинацией до конца**. Порядок (ниже детально): **обнаружить
операции → взять auth → реплеить (с пагинацией, если полный) → разрешить
словари → проверить `errors` → сверить с `get_page_text`.**

## B0. Обнаружение операций — не угадывать, а смотреть

Полный список операций, которые карточка реально вызвала, берётся из
`performance` (никакого перебора «какие бывают»):

```js
[...new Set(performance.getEntriesByType('resource')
  .map(e => { try { const u = new URL(e.name);
    return /graphql/i.test(u.pathname) ? u.searchParams.get('queryName') : null;
  } catch (_) { return null; } })
  .filter(Boolean))].sort()
```

Чтобы список был полным — **прокликать все секции и drawers один раз**
(вкладки, оба под-вида Сегментов, Активность+Баллы, «История
идентификаторов», «Все устройства», развернуть запись ленты). Операции,
которые до этого не вызывались, в `performance` не появятся.

## B1. Каталог операций (что покрывает)

Все берут `customerId` (= Mindbox ID), кроме словарей/контекста.

**Ядро карточки**

| Секция | operationName | особенности |
| --- | --- | --- |
| Шапка | `CustomerQuery`, `CustomerBasicDataQuery` | контакты, ID, устройства, данные покупок; `shouldUnmaskPersonalData` |
| Лента → Активность | `CustomerActivityDataQuery` | cursor-пагинация; `sortOptions{sortBy:"DateTime",direction:"Descending"}`, `filterOptions{customerActivityFilter:[...]}` |
| Лента → Баллы | `BalancesQuery`, `IsAnyBalancesExistQuery` | балльные счета и движения |
| Подписки | `CustomerSubscriptionsQuery` | статусы по каналам/тематикам |
| Сегменты → Текущие | `CustomerSegmentsDataQuery` | `segments[]{segment{id…}, segmentation{id…}, changeDateTimeUtc}` |
| Сегменты → История | `CustomerSegmentationHistoryDataQuery` | вход/выход + причина |
| История изменений | `CustomerHistoryDataQuery` | before/after; cursor-пагинация, `filterOptions` |
| Доп. поля | `CustomerAdditionalDataQuery` | `customFields[]` с `customFieldKindId` |
| Списки продуктов | `CustomerProductListsQuery` | `productLists[]{id,internalId,name}` |
| Карты | `CustomerDiscountCardsTotalCountQuery` | счётчик карт |

**Drawers (только по клику — легко пропустить)**

| Элемент | operationName |
| --- | --- |
| «История идентификаторов» (`?drawer=id-history`) | `CustomerMindboxIdHistory`, `CustomerExternalIdHistoryQuery`, `CustomerIdHistoryTotalCount` |
| «Все устройства» (`?drawer=push-and-devices`) | `CustomerLastMobileAppInstallations`, `CustomerWebsiteActivities`, `CustomersWithSameDevices` |

**Словари для джойнов id→имя (без них видны только числа)**

| operationName | разрешает |
| --- | --- |
| `CustomFieldKindsQuery` | `customFieldKindId` → **имя доп. поля** |
| `MailingListQuery`, `MailingChannelsQuery`, `MailingStatusesByCustomerIdFilterQuery` | id рассылки/канала/статуса → имена |

**Проектный контекст (меняет трактовку данных)**

`IsMultibrandProject`, `BrandsQuery`, `ProjectSystemNameQuery`, `getSettings` —
мультибренд/таймзона/валюта. На мультибрендовом проекте поля и регистрация
читаются с привязкой к бренду.

## B2. Реплей (auth + текст запроса)

`Authorization` короткоживущий и в `get_page_text` не виден — **захвати из
живого запроса** и переиспользуй. `query`-текст и значения enum'ов тоже
бери из захваченного запроса (см. «грабли перехвата»), не реконструируй:

```js
const r = await fetch('/graphql?queryName=' + op, {
  method: 'POST', credentials: 'include',
  headers,                                   // с Authorization из живого запроса
  body: JSON.stringify({ operationName: op, query: queryText, variables })
});
const json = await r.json();
if (json.errors) { /* НЕ трактуй null как "значения нет" — это отказ/ошибка */ }
```

Со сменой только `customerId` операция портируется на любого клиента
(проверено). Возвращай из JS **очищенные структуры/счётчики**, не сырой
ответ (фильтр расширения режет трекинг-URL внутри — `[BLOCKED]`).

## B3. Правила полноты (иначе теряешь молча)

1. **Пагинация до конца.** Лента, история изменений, история сегментов —
   cursor-пагинация (`pageInfo.hasNextPage` + `endCursor.value`). Одна
   страница = окно, а не вся жизнь клиента. Для аудита «с момента прихода»
   идём по курсору до `hasNextPage:false`.
2. **Полиморфизм ленты.** `activity.nodes` — union по `__typename`:
   `CustomerMessage`, `CustomerMessageSentStatus` / `OpenedStatus` /
   `NotDeliveredStatus`, `CustomerAction`, `EditingCustomerChange` (заказы =
   `CustomerAction` «Изменение заказа …»). Набор типов **зависит от
   клиента** (у одного 3, у другого 6) — не считай по одному образцу, что
   видел всё. Поля приходят только для типов, на которые в запросе есть
   инлайн-фрагмент.
3. **⚠️ Лента — журнал на момент события, не текущее состояние.** Каждый
   статус письма (Отправлено/Открыто/Не доставлено) — **отдельная
   неизменяемая нода со своим `dateTimeUtc`**. Текущее состояние заказа
   берётся с самого заказа, а не выводится из ленты.
4. **Словари и `errors`** — разрешай id→имя (B1) и всегда проверяй массив
   `errors` (частичные данные: `data` есть, поле `null` + ошибка).
5. **Маскирование.** `shouldUnmaskPersonalData:false` (как UI). Полные ПД
   приходят при пермиссии «Просмотр ПД»; иначе значения маскированы —
   маска ≠ «значение». См. `../docs/pages/enterprise-security.md`.

## Аудит коммуникации (типовой запрос «почему получил/не получил»)

Авторитетная цепочка, всё с пагинацией до нужной даты:

- **Лента (Активность)** — все `CustomerMessage*` по этой рассылке:
  отправлено / доставлено / открыто / **не доставлено** (+ причина из
  развёрнутой записи / `EmailMessageQuery`);
- **Подписки** — был ли клиент подписан на канал/тематику в тот момент;
- **Сегменты → История** — входил ли клиент в таргет-сегмент на момент
  отправки (`CustomerSegmentationHistoryDataQuery`, причина перехода);
- **История изменений** — не менялись ли контакты/поля, влияющие на отбор.

## Грабли / тупики (проверено)

- `/graphql/` без `?queryName=<Op>` → HTML; cookie без `Authorization` → `401`.
- **Интроспекция отключена** — enum (`CustomerActivitySortFields` = `DateTime`,
  не `DateTimeUtc`) и обязательные поля input'ов узнаются из живого запроса
  или текста ошибки («required input field … is missing»). Не угадывай.
- **Перехват `window.fetch` хрупок по таймингу.** Модули, загруженные **до**
  патча (шапка + лента активности на初 загрузке), держат раннюю ссылку на
  `fetch` и **обходят** перехватчик; лениво-подгружаемые (drawer, первый
  клик по вкладке) — ловятся. Поэтому для полноты надёжнее
  **`performance`-обнаружение (B0) + реплей (B2)**, а не один перехват.
  Если перехватываешь — патч до начала взаимодействий, и провоцируй
  свежие запросы (первый клик по вкладке, смена фильтра, пагинация).
- **Повторный заход на вкладку** берёт данные из SPA-кэша → перехватчик
  свежий запрос не видит.
- Фильтр расширения режет сырые строки с URL/токенами (`[BLOCKED]`) — в
  ответах ленты есть трекинг-ссылки и `gateKey.templatePreviewUrl`.
  Возвращай из JS структуру/счётчики/base64, не сырой ответ.
- `__APOLLO_CLIENT__.cache` по клиенту пуст — это не тот клиент.

## Стоимость

Быстрый обзор: `get_page_text` (секунды). Полный дамп: `get_page_text` +
по 1 `fetch` на секцию + пагинация. Наивный путь (клики/скриншоты/
развороты) — десятки действий и минуты, при этом `internalId` сегментов и
история переходов из UI не доставались в принципе.

## Верификация (что реально проверено)

`usmall.mindbox.ru` (2026-06-19), клиенты `78317817`, `78317773`, `78317684`.
Все реплеи — статус `200`, `errors` пуст.

- **Сегменты (`78317773`):** реплей `CustomerSegmentsDataQuery` → 26
  сегментов = 26 имён в DOM (полный паритет), `internalId` в данных есть и
  **скрыт** в UI. Реплей = UI + больше.
- **История изменений (`78317684`):** реплей → 7 нод, `hasNextPage:false` =
  7 записей в UI (полный паритет), before/after на месте, история доходит
  до **регистрации клиента** — то есть «с момента прихода в базу» снимается
  целиком.
- **Доп. поля (`78317684`):** реплей → 3 поля, но только `customFieldKindId`
  `[43,101,113]` — **без имён**; UI показывает те же 3 поля **с именами**
  («Баланс клиента», «Реферальные друзья», LC-поле). Подтверждает: имена
  нужно джойнить из `CustomFieldKindsQuery`; одиночный реплей даст «поле 43
  = 500». («Баланс клиента» = доп. поле, **не** лояльные баллы.)
- **Подписки (`78317684`):** реплей `CustomerSubscriptionsQuery` → 1 запись
  (Email «Отписан») = состояние в UI; полную матрицу брендов/каналов UI
  достраивает джойном `SubscriptionsQuery` + `BrandsQuery`.
- **Баллы (`78317684`):** реплей `BalancesQuery` пуст = UI «Нет баллов».
- **Лента до конца (`78317684`):** прокручена пагинацией до первого события
  (`18.05.2026 21:36 Просмотр продукта`) — полный таймлайн достижим.
- **Переносимость:** реплеи для трёх клиентов сменой только `customerId` →
  `200` + реальные данные.
- **Обнаружены пропущенные операции** (через `performance`): drawers
  идентификаторов и устройств, словарь `CustomFieldKindsQuery`, проектный
  контекст `IsMultibrandProject` — их нет в «наивном» списке вкладок.
- **Остаётся непроверенным:** полный набор `__typename` ленты на клиенте с
  заказами/возвратами; структура `BalancesQuery` на клиенте **с** баллами
  (у всех троих баллов нет). По этим двум держать выводы как «вероятно».

## Оговорки

- `operationName` — публичный контракт UI, относительно стабилен; `query` и
  enum'ы меняются от сборки — бери из живого запроса, не хардкодь.
- `Authorization`-токен короткоживущий — захватывай из текущей сессии.
- ФИО/email/телефоны в командные заметки не выносим — только структура и
  при необходимости Mindbox ID.
- Соседи: `react-flow-extraction.md`, `personalization-extraction.md`,
  `ui-quirks.md`. История сегментов связана с
  `../../knowledge/reference/mindbox-пересчёт-сегментов.md`
  (воркспейс CRM, вне этого репо).
