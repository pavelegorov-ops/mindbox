Маркетолог хочет сохранить свою работу — закоммитить и запушить
изменения в приватный репозиторий своего тенанта. Эта команда не
трогает основной репо движка (для него отдельный workflow).

## Шаг 1. Понять, какой тенант активен

```bash
ls -1 private/ 2>/dev/null | grep -v '^_template$' | grep -v '^\.' | head -1
```

Если пусто — отчитайся `Активного тенанта нет — нечего отправлять.` и
останавливайся. Иначе запомни как `<tenant>`.

## Шаг 2. Посмотреть статус приватного репо

```bash
git -C private/<tenant> status --porcelain
```

Если пусто — `В private/<tenant> нет несохранённых изменений. Нечего
отправлять.` — остановись.

Иначе разбери результат: `M` — изменён, `??` — новый, `D` — удалён,
`A` — уже добавлен в индекс. Сгруппируй по тому, что лежит в каких
подпапках (`scenarios/src/`, `scenarios/rendered/`, `mailing-parameters/`,
`backlog/`).

## Шаг 3. Перегенерировать сценарии и убедиться, что валидно

Если среди изменённых есть что-то под `scenarios/src/` — обязательно
прогони генератор:

```bash
.venv/Scripts/python.exe scripts/render_scenarios.py
```

Если выходной код = 1 (валидация упала) — **остановись**, покажи
ошибки из вывода и попроси пользователя исправить YAML. Не предлагай
коммитить невалидное.

Если выходной код = 0, но в `scenarios/rendered/` появились новые
изменения (генератор перезаписал .md) — добавь их к статусу из шага 2.

## Шаг 4. Спросить про commit message

Покажи пользователю diff-summary в человеческом виде:

> Изменения в `private/<tenant>/`:
>
> - 🆕 1 новый сценарий: `Sc_NewYear_Promo_2026.yaml` + его rendered/.md
> - ~ изменён `Warming-Up-2Order.yaml`
> - ~ перегенерил `INDEX.md`, `dependencies.md`
>
> Что напишем в commit message? (Если просто скажешь «как обычно» —
> я сгенерирую короткое описание из diff.)

Жди ответа. Если ответ типа «как обычно», «сделай сам», «придумай» —
сгенерируй сам по образцу:

```
add scenario Sc_NewYear_Promo_2026 + tweak Warming-Up-2Order
```

(одна короткая строка, на русском или английском — подстраивайся под
стиль предыдущих коммитов: `git -C private/<tenant> log --oneline -5`).

## Шаг 5. Коммит и push

```bash
git -C private/<tenant> add -A
git -C private/<tenant> commit -m "<message>"
git -C private/<tenant> push
```

Если push упал из-за того, что коллега уже закоммитил параллельно
(non-fast-forward / fetch first):

```bash
git -C private/<tenant> pull --rebase
```

Если rebase прошёл чисто — повтори push. Если есть конфликты —
**остановись**, покажи список конфликтных файлов и объясни:

> ⚠️ Кто-то из коллег закоммитил параллельно, и нам предложили
> объединить ветки. В этих файлах есть конфликты:
>
> ```
> scenarios/src/Foo.yaml
> ```
>
> Я могу помочь разобрать каждый конфликт по очереди — открыть файл
> и предложить, какую версию оставить (твою, чужую или объединить).
> Или ты предпочитаешь сделать это сам в редакторе? После
> разрешения — `git -C private/<tenant> add <файл>` и
> `git -C private/<tenant> rebase --continue`, потом снова
> `/отправь-данные`.

## Шаг 6. Финальный отчёт

Кратко:

> ✅ Готово. Запушил <N> файлов в `private/<tenant>` коммитом
> `<сокращённый sha>`: «<message>».
>
> Чтобы коллеги это увидели у себя — пусть вызовут `/обнови-данные`.

## Что НЕ делает эта команда

- Не трогает основной репо движка. Если ты редактировала `notes/` или
  `CLAUDE.md` или скрейперы — это другой репо, для него нужен обычный
  `git commit` и `git push` руками (или попроси Клода сделать в этом же
  чате).
- Не делает force-push, не сбрасывает чужие коммиты.
- Не запускает `/sync-docs` — корпуса доков синхронизируются отдельной
  командой.
