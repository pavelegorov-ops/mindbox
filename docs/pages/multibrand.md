# Мультибренд

Включение мультибренда позволяет объединить на проекте несколько баз данных в одну.  
Для каждого бренда можно настроить права доступа, подписки, отправителей. Отчетность также разделена по брендам. Подключение модулей и биллинг — общие.

## Как включить бренд

1. На вкладке **Настройки** → **Системные** → **Бренды** нажмите «Добавить»:

   ![бренд11.png](https://storage.yandexcloud.net/assets-help-mindbox-ru/images/%D0%B1%D1%80%D0%B5%D0%BD%D0%B411.png)
2. Укажите название, системное имя и отрасль бренда и нажмите «Сохранить».

   ![Снимок экрана 2023-06-22 в 13.15.51.png](https://storage.yandexcloud.net/assets-help-mindbox-ru/images/%D0%A1%D0%BD%D0%B8%D0%BC%D0%BE%D0%BA%20%D1%8D%D0%BA%D1%80%D0%B0%D0%BD%D0%B0%202023-06-22%20%D0%B2%2013.15.51%281%29.png)

   Выбор отрасли влияет на то, с какими данными будут сравниваться показатели в отчете [«Здоровье Email»](%D0%BE%D1%82%D1%87%D0%B5%D1%82-%D0%B7%D0%B4%D0%BE%D1%80%D0%BE%D0%B2%D1%8C%D0%B5-email.md).
3. Сделайте необходимые изменения в соответствии с таблицей ниже.

### Изменения при включении бренда

Что происходит с текущими сущностями на проекте после добавления первого дополнительного бренда и какие шаги нужно выполнить для его включения в работу.

| Сущность | Текущие механики | Что поправить | Что поменяется в создании новых механик |
| --- | --- | --- | --- |
| **Подписки в карточках клиентов** | Остаются у первого бренда | Значения подписок по новому бренду нужно прописывать отдельно | Нужно будет указывать бренд при любом изменении подписки клиента |
| **Действия клиентов** | Остаются у первого бренда | Ничего | Нужно будет выбирать бренд или точку интеграции при выдаче любых действий |
| **Сохраненные фильтры «Клиент — Подписка»** | Ставится по первому бренду. Например, фильтр «Подписка — Подписан без учета канала и тематики» станет «Подписка — Подписан в Бренде1 без учета канала и тематики» | Поправить фильтры и сегменты при необходимости учитывать подписки в разных брендах | Нужно будет указывать бренд в любых фильтрах по подписке |
| **Сохраненные фильтры «Действие — Регистрация» и «Действие — Первое взаимодействие»** | Ставится «в любом бренде». Например, фильтр «Действие клиента — Регистрация клиента» станет «Действие клиента — Регистрация клиента в любом бренде» | Поправить фильтры и сегменты при необходимости фильтрации по конкретному бренду | Можно будет указывать бренд в фильтрах по регистрации и первому взаимодействию или разрешать все бренды |
| **Сегменты РФМ** | Остаются у первого бренда | При необходимости добавить РФМ-сегменты по новому бренду | Нужно будет указывать бренд при создании |
| **Продукты; YML-фиды** | Остаются у первого бренда | При необходимости наполнить новый бренд продуктами | Нужно будет указывать бренд при добавлении продуктов и фидов |
| **Рассылки** | Остаются у первого бренда | При необходимости создать или продублировать рассылки в новом бренде | Нужно будет указывать бренд при создании рассылок |
| **Попапы, встроенные блоки, виджеты** | Берут бренд из точки интеграции сайта. Все точки интеграции остаются у первого бренда | При необходимости создать формы для нового бренда. При использовании пользовательского js могут понадобиться изменения при использовании определенных операций (см. п. Спецификации операций) | Ничего не меняется, нужно будет выбирать сайт показа |
| **In-App** | Берет бренд из точки интеграции приложения. Все точки интеграции остаются у первого бренда | При необходимости создать In-App’ы для нового бренда | Ничего не меняется, нужно будет выбирать приложение |
| **Сценарии по событию** | Остаются у первого бренда. Бренд влияет на то, какие события обрабатываются и с каким брендом выдаются действия из групп шагов. Подробнее о том, как меняется работа сценариев в зависимости от типа события — [в разделе ниже](multibrand.md#sobytiya-v-scenariyah) | При необходимости продублируйте сценарии в новом бренде или, наоборот, ограничьте выборку условиями по нужному бренду (например, подписками или точками контакта) | Нужно будет указывать бренд при создании |
| **Сценарии по расписанию** | Остаются у первого бренда. Так как у данных сценариев нет запускающего события, они срабатывают по всем клиентам, подходящим под условия в фильтре расписания | При необходимости ограничьте выборку сценариев (например, подписками или точками контакта) | Нужно будет указывать бренд при создании |
| **Пулы / Балльные счета / Голосования** | Сущности не связаны с брендом | Ничего | Ничего не меняется |
| **Операции** | Берут бренд из точки интеграции. Все точки интеграции остаются у первого бренда | При необходимости добавить точки интеграций нового бренда в общие операции, создать собственные операции для бренда | Ничего не меняется, нужно будет выбирать точку интеграции |
| **Спецификации операций** | - В операциях с передачей подписки (шаги «Клиент — Зарегистрировать» / «Клиент — Авторизованный — Дополнить» / «Авторизованный — Редактировать» / «Неавторизованный — Зарегистрировать или Дополнить» / «Клиент — Импортировать» / «Клиент — Создать и подписать на рассылки») при передаче узла `subscriptions` без уточнения по бренду (`brand`), клиент будет подписан на бренд из точки интеграции. Все точки интеграции остаются у первого бренда. - в шагах с подпиской вручную («Клиент — Авторизованный — Редактировать» и «Клиент — Неавторизованный — Редактировать») будет указан первый бренд проекта. - в операциях с возвратом данных («Клиент — Получить данные по текущему клиенту» / «Действие — Связать клиентов»), если не был уточнен бренд, данные будут возвращаться по всем брендам. - в экспортах появляются новые поля:   - Выгрузить дисконтные карты клиентов — `discountCards/ discountCard/ customer/ subscriptions/ subscription/ brand`   - Выгрузить клиентов — `customers/ customer/ subscriptions/ subscription/ brand`   - Выгрузить объединения клиентов — `customerMerges/ customerMerge/ resultingCustomer/ subscriptions/ subscription/ brand` | Проверьте настройки операций с данными шагами, укажите бренды или разрешите любые там, где необходимо | Можно будет указывать бренд в интеграциях и разделять действия по брендам или, наоборот, в одном вызове править данные по нескольким брендам |
| **Папки** | Разрешены все бренды | Можно ограничить текущие папки по бренду. Тогда рассылки и сценарии можно будет создавать только в разрешенном бренде и только сотрудникам, у которых разрешен тот же бренд | Можно будет ограничивать папки по бренду. Тогда рассылки и сценарии можно будет создавать только в разрешенном бренде и только сотрудникам, у которых разрешен тот же бренд |
| **Промоакции** | Не связаны с брендами | Можно ограничить по каналам, чтобы акции действовали только на сайтах и офлайне нужного бренда | В создании акций ничего не меняется. Можно будет ограничивать по каналам, чтобы акции действовали только на сайтах и офлайне нужного бренда |
| **Дисконтные карты** | Не связаны с брендами | Можно разделить по типам | В создании ничего не меняется. Можно будет разделять по типам |
| **Продуктовые рекомендации** | Алгоритмы рекомендаций автоматически учитывают бренд продукта | Ничего | Ничего |
| **АБ-тесты по сегментам клиентов** | Бренд не учитывается, но, так как тесты используются в кампаниях конкретного бренда, это не влияет на определение победившего варианта АБ-теста | Ничего | Ничего |
| **АБ-тесты на посетителей сайта** | Берут бренд из точки интеграции | При необходимости создайте тесты для нового бренда | Ничего не меняется, нужно будет выбирать сайт теста |
| **Отчеты** | При просмотре можно выбирать нужный бренд | Ничего | Ничего |
| **Подписка на отчеты** | Остается по первому бренду | При необходимости переподпишитесь или добавьте подписку по новому бренду | При подписке нужно будет указывать бренд |
| **Точки интеграции** | Остаются у первого бренда | Создайте точки для нового бренда, при необходимости укажите их в существующих операциях или создайте для них отдельные | Нужно будет указывать бренд при создании |
| **FTP-импорт** | Остаются у первого бренда | Продублируйте при необходимости для нового бренда | Нужно будет указывать бренд при создании |
| **FTP-экспорт** | Бренд не указывается в настройке FTP, но может появиться в самих экспортах в зависимости от используемой операции:  - Выгрузить дисконтные карты клиентов — `discountCards/ discountCard/ customer/ subscriptions/ subscription/ brand` - Выгрузить клиентов — `customers/ customer/ subscriptions/ subscription/ brand` - Выгрузить объединения клиентов — `customerMerges/ customerMerge/ resultingCustomer/ subscriptions/ subscription/ brand` | Ничего | Ничего |
| **Вызовы по API** | В вызовах всегда передается `endpointId` (точка интеграции) — по нему определяется бренд. [Импорт продуктов](https://developers.mindbox.ru/docs/prodimportcsv) затребует передачу бренда в URL или теле запроса | Настройте вызовы по точкам интеграций нового бренда. Добавьте бренд в импорты продуктов | Ничего, нужно будет указывать в вызовах точку интеграции бренда. Обязательно нужно будет передавать бренд в импорте продуктов |
| **SMPP-соединения** | Остаются у первого бренда | Добавьте для нового бренда при необходимости | Нужно будет указывать бренд при создании |
| **Вебхуки** | Не используют бренды, но в теле запроса может понадобиться указание бренда при передаче подписки (см. п. Спецификации операций) | Проверьте, есть ли в вызовах передача подписок; при необходимости добавьте бренд | В теле вебхука можно будет уточнять бренд при передаче подписок |
| **Шаблоны действия** | Разрешены во всех брендах | Ничего | Можно будет разрешать только в отдельных брендах |
| **Каналы и точки контакта** | Не разделены по брендам | Можно добавить для нового бренда, например, чтобы ограничивать промоакции | Ничего |
| **Персонал** | Разрешены все бренды | Можно ограничить текущих сотрудников по бренду. Тогда они смогут создавать рассылки и сценарии только в данном бренде. Строить фильтры можно будет только по своему бренду | При создании персонала можно будет ограничивать доступ по бренду. Тогда они смогут создать рассылки и сценарии только в своем бренде. Строить фильтры можно будет только по своему бренду |
| **Пермиссии** | Для создания рассылок и сценариев понадобится пермиссия «Просмотр брендов» | Добавьте нужному персоналу и группам безопасности пермиссию «Просмотр брендов» | При создании персонала и пользовательских групп безопасности для доступа к созданию рассылок и сценариев нужно будет выдавать пермиссию «Просмотр брендов» |
| **Участники программы лояльности** | Остаются у первого бренда | При необходимости задайте для нового бренда | Нужно выбирать бренд при настройке |
| **Контроль частоты попапов** | Общий по проекту, нет деления по брендам | Ничего | Ничего |
| **Атрибуция заказов** | Автоматически работает в рамках бренда | Ничего | Ничего |
| **Параметры платформы** | Нет деления по брендам | Ничего | Ничего |
| **Зоны** | Нет деления по брендам | Ничего | Ничего |
| **Настройки Email — Отправители и подписи DKIM** | Остаются у первого бренда | Добавьте отправителей для нового бренда | Отправители будут создаваться в рамках конкретного бренда |
| **Настройки Email — Подтверждение подписки** | Текущие настройки остаются у первого бренда. Новый бренд создается с выключенным подтверждением подписки | Настройте подтверждение подписки на новом бренде или оставьте выключенным | Подтверждение можно включать и выключать на брендах независимо друг от друга |
| **Настройки SMS — Подтверждение подписки** | Текущие настройки остаются у первого бренда. Новый бренд создается с выключенным подтверждением подписки | Настройте подтверждение подписки на новом бренде или оставьте выключенным | Подтверждение можно включать и выключать на брендах независимо друг от друга |
| **UTM-метки** | Остаются у первого бренда. Новому автоматически прописываются стандартные (utm_campaign — `${Message.MailingUtmName}`; utm_source — mindbox; utm_medium — email) | Поправьте метки для Email и пропишите для вебпушей на новом бренде при необходимости | Метки можно будет настраивать на брендах независимо друг от друга |
| **Тематики** | Остаются у первого бренда | Добавьте тематики для нового бренда при необходимости | Тематики будут создаваться в рамках конкретного бренда |
| **Контрольная группа** | Не учитывает бренд, так как клиент может контактировать сразу с несколькими брендами | Ничего | Ничего |
| **Автоудаление** | Фильтры с подписками ставятся по первому бренду. Например, фильтр «Подписка — Подписан без учета канала и тематики» станет «Подписка — Подписан в Бренде1 без учета канала и тематики». Фильтры «Действие — Регистрация» и «Действие — Первое взаимодействие» ставятся «в любом бренде». Например, фильтр «Действие клиента — Регистрация клиента» станет «Действие клиента — Регистрация клиента в любом бренде» | При необходимости поправьте фильтры автоудаления с данными условиями | При создании критериев автоудаления в фильтрах нужно будет указывать бренд |
| **Анкета** | Не делится по брендам | Ничего | Ничего |

### События в сценариях

Все сценарии принадлежат какому-либо бренду. То, на какие действия отрабатывает сценарий, зависит от типа события.

Срабатывают только **по действиям в бренде** сценария:

- Выдано действие
- Выдано действие связанное с продуктом
- Клиент покинул сайт или приложение
- Клиент запросил код авторизации
- Статус заказа изменен
- Данные заказа изменены
- Новый заказ
- Статус подписки изменен
- Новый клиент
- Значение дополнительного поля клиента изменено
- Данные клиента изменены
- Клиент зарегистрировался
- Клиент подтвердил email
- Клиент изменил email
- Клиент подтвердил мобильный телефон
- Клиент изменил мобильный телефон
- Клиент изменил данные
- Карточки одного клиента объединены
- Клиент применил промокод
- Изменения заданного баланса
- Бонусные баллы стали доступны (перешли из заблокированных)
- Выдан промокод
- Статус дисконтной карты изменен
- Дисконтная карта заменена
- Использован реферальный промокод клиента
- Баланс клиента стал отрицательным
- Клиенту отправлена рассылка
- Для клиента сформировано письмо в рассылке

Срабатывают только по событиям **с продуктом в бренде** сценария:

- Продукт в заказе доставлен
- Продукт в заказе оплачен
- Предпочитаемый продукт изменился
- Продукт в списке продуктов изменился
- Просмотренный продукт изменился

**Игнорируют** бренд и срабатывают по всем брендам:

- Список продуктов изменился
- Клиент попал в сегмент
- Клиент вышел из сегментации
- Настало время Лучшего следующего предложения

Если в сценариях из последней группы нужно разделять клиентов по брендам, добавьте дополнительные проверки с помощью блоков «Условие».

## Как отключить бренд

Перед отключением нужно будет удалить или отредактировать связанные с брендом сущности:

- рассылки в статусах «Готова к отправке», «Готова к использованию» (черновики и завершенные рассылки можно не трогать, но клики по уже отправленным рассылкам в бренде приходить не будут);
- сценарии;
- товарные фиды;
- папки, ограниченные брендом;
- подписки на отчеты по бренду;

### Изменения при отключении бренда

Что происходит с текущими сущностями на проекте, связанными с деактивированным брендом.

| Сущность | Текущие механики |
| --- | --- |
| **Подписки клиентов в карточках** | Не выводятся в карточке. Остаются в фильтрах, если на проекте от двух брендов. Если остается один бренд, то не выводится и в фильтрах |
| **Сохраненные фильтры «Клиент — Подписка в бренде»** | Фильтры сохраняются, если на проекте от двух брендов. Если остается один бренд, то меняются на «Клиент — Подписка» |
| **Сохраненные фильтры «Действие — Регистрация в бренде» и «Действие — Первое взаимодействие в бренде** | Фильтры сохраняются, если на проекте от двух брендов. Если остается один бренд, то меняются на «Действие — Регистрация» и «Действие — Первое взаимодействие» |
| **Сохраненные фильтры «Действие — Бренд»** | Фильтры по бренду действия сохраняются, даже если на проекте остается один активный бренд |
| **Продукты** | Продукты сохраняются |
| **Рассылки** | Завершенные и остановленные рассылки и черновики остаются в деактивированном бренде |
| **Спецификации операций** | Данные по неактивному бренду приниматься не будут. Если на проекте остается один активный бренд:  - в операциях с передачей подписки (шаги «Клиент — Зарегистрировать» / «Клиент — Авторизованный — Дополнить» / «Авторизованный — Редактировать» / «Неавторизованный — Зарегистрировать или Дополнить» / «Клиент — Импортировать» / «Клиент — Создать и подписать на рассылки») можно продолжать указывать активный бренд (brand) в узле subscriptions. - в операциях с возвратом данных («Клиент — Получить данные по текущему клиенту» / «Действие — Связать клиентов») пропадет поле /customer/subscriptions/subscription/pointOfContact - в экспортах пропадут поля:   - Выгрузить дисконтные карты клиентов — `discountCards/ discountCard/ customer/ subscriptions/ subscription/ brand`   - Выгрузить клиентов — `customers/ customer/ subscriptions/ subscription/ brand`   - Выгрузить объединения клиентов — `customerMerges/ customerMerge/ resultingCustomer/ subscriptions/ subscription/ brand` |
| **FTP-экспорт** | Если на проекте остается один активный бренд, из экспортов операций пропадут поля:  - Выгрузить дисконтные карты клиентов — `discountCards/ discountCard/ customer/ subscriptions/ subscription/ brand` - Выгрузить клиентов — `customers/ customer/ subscriptions/ subscription/ brand` - Выгрузить объединения клиентов — `customerMerges/ customerMerge/ resultingCustomer/ subscriptions/ subscription/ brand` |
| **Вызовы по API** | Вызовы по удаленным endpointId (точки интеграции) будут падать с ошибкой. В [импорте продуктов](https://developers.mindbox.ru/docs/prodimportcsv) продуктов можно продолжать передавать бренд, но только активный |
| **Настройки Email и SMS, SMPP-соединения** | Настройки по деактивированному бренду скрыты |
| **Вебхуки** | Не используют бренды, но в теле запроса может быть передача данных по деактивированному бренду |
| **Персонал** | Персонал может быть ограничен неактивным брендом. При необходимости поменяйте доступы |
| **Пермиссии** | Если на проекте остался один активный бренд, для создания рассылок и сценариев больше не нужна будет пермиссия «Просмотр брендов» |
| **Отчеты** | Отчеты по деактивированным брендам скрыты |
